Linux Mentor - Architecture and System Design

Status
------
This document records the current implementation and the agreed product direction.
It distinguishes working integration points from planned components.

Product objective
-----------------
Linux Mentor is an educational assistant for Antigravity CLI. It should help
learners reason through Linux troubleshooting and system concepts using concise,
Socratic guidance, not automate the learner's work. Distro-specific guidance
uses the active Linux distribution's installed documentation where available;
coverage depends on local documentation packages. The intended audience includes
university learners.

Current decisions
-----------------
- Antigravity is the target host; Gemini CLI is no longer the target.
- The MCP integration is written in Go and uses stdio.
- A desktop chat UI is intended to keep assistant explanations and questions
  out of the terminal. The user's interaction remains in Antigravity for now;
  sending user messages from the UI is out of scope.
- The planned UI stack is Wails with TypeScript and React.
- The UI should display assistant responses only, not mirror the user's prompts.
- The session-start hook is the entry point for launching the UI and handing
  it the active Antigravity conversation context.
- The frontend's `index.html` is only Vite's mount document embedded in the
  Wails window. The product UI runs in the native desktop application's webview;
  no standalone browser app or web server is part of the runtime.

Implemented
-----------
- `cmd/mcp-server/main.go` serves MCP tools over stdio. `get_status` is a
  connectivity check, and progress and preference tools use the local SQLite store.
- `hooks.json` enables the `SessionStart` hook.
- `scripts/on-session-start.sh` reads the hook's JSON input, validates the
  conversation ID and transcript path, starts the configured GUI process, and
  emits `{}` on stdout to satisfy the hook protocol.
- The launcher defaults to `build/bin/linux-mentor`. Set `LINUX_MENTOR_GUI` to
  override that executable. The launcher passes `LINUX_MENTOR_CONVERSATION_ID`
  and `LINUX_MENTOR_TRANSCRIPT_PATH` to the process environment.
- Launcher output is written to
  `${XDG_STATE_HOME:-~/.local/state}/linux-mentor/gui.log`; hook stdout is
  reserved for JSON.
- `cmd/desktop` is the Wails host. It embeds the React production assets and
  exposes session context and transcript messages to the frontend.
- The Go host watches the active transcript incrementally and exposes only
  completed `PLANNER_RESPONSE` records from `MODEL`. The UI polls that bridge
  and renders mentor responses without mirroring user input.
- `scripts/build-desktop.sh` builds the React assets and packages the Wails
  executable at the hook's default launch path.
- The desktop app and MCP server share the per-user SQLite database. The GUI
  creates/updates session metadata; the MCP tools persist evaluations and
  interaction preferences.

Response flow and limitations
-----------------------------
The read-only response path is:

  Antigravity writes conversation transcript
      -> Wails host reads completed JSONL records
      -> React UI polls the Go bridge and renders model responses

The transcript schema is Antigravity-specific. The current reader intentionally
filters to completed `PLANNER_RESPONSE` records whose source is `MODEL`.
Keep this mapping covered by tests if Antigravity changes its transcript format.
The executable must be built before the hook can launch it.

Not implemented
---------------
- Packaging, installation, and a cross-distribution release process.

Offline Documentation & Spaced Repetition Design
------------------------------------------------
1. Local Documentation Retrieval:
   - The MCP server creates `${XDG_DATA_HOME:-~/.local/share}/linux-mentor/docs.db`
     on first launch and reads the active distro's exact `ID` from `/etc/os-release`.
   - It indexes installed man pages and selected text documentation from standard
     `/usr/share` and `/usr/local/share` locations. Text is stored once with a
     SQLite token-frequency index for local ranking.
   - `search_docs` searches only rows tagged with the detected distro ID and returns
     up to five short excerpts with local source paths. It does not fall back to
     `ID_LIKE` or another distro's docs. The index refreshes every 30 days.
   - Coverage depends on documentation installed on the user's system; this does
     not download or bundle a complete official documentation corpus.

2. Student Progress & Spaced Repetition:
   - Stored locally at `${XDG_STATE_HOME:-~/.local/state}/linux-mentor/progress.db`.
   - The database is created and schema-migrated on the first desktop or MCP-server
     launch. SQLite is the sole persistence format; the database and its directory
     are restricted to the current OS user.
   - `sessions` keeps conversation IDs and start/activity/end timestamps, not
     transcript contents. `concepts` stores current scheduling state and its
     creation date. `attempts` is the source of truth for individual answers.
     `review_blocks` groups each run of misses through its next correct answer,
     preserving the exact miss total for that review; concept summaries derive
     current misses from the open block and cap previous misses at 2.
   - `user_preferences` stores interaction style, tone, response length, and
     optional learner-authored notes. These preferences are personalization only
     and cannot override safety or higher-priority instructions.
   - No MAC address or other hardware identifier is collected.
   - Review intervals are 14/28/56 days after a clean success, 2/4/8 days after
     one miss, and 1/2/4 days after two or more misses. Unresolved misses are
     immediately eligible for reinforcement.

3. Desktop UI as Study Guide & Reference Sheet:
   - Desktop UI in `cmd/desktop` serves as a learning companion and study guide.
   - Surfaces practiced commands cheat sheet, mastered concepts, active review queue,
     and flagged areas for improvement.

4. MCP Server Tools (`cmd/mcp-server/main.go`):
   - `get_status`: Server health check.
   - `search_docs`: Ranked local-document retrieval, scoped to the detected distro.
   - `get_learning_status`: Active review queue and mastered topics.
   - `record_evaluation`: Record command accuracy and explanation depth milestones.
   - `get_user_preferences` and `save_user_preferences`: Read/write local
     interaction preferences when requested by the learner.

Design constraints
------------------
- Keep MCP stdio protocol output separate from logs; never write diagnostics to
  the MCP server's stdout.
- Keep Antigravity hook stdout valid JSON. Launcher diagnostics go to stderr;
  the detached GUI's output goes to its state log.
- Treat the transcript as read-only input. Do not modify Antigravity's logs or
  automatically run commands from transcript content.
- Keep assistant-response display independent of the MCP server. The MCP server
  provides tools to Antigravity; the transcript is the current candidate
  transport from Antigravity to the UI.
- Keep storage local and use the existing transcript rather than introducing a
  network service or forwarding all chat content through another API.
